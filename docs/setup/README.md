# Pointing the Twin at Another Client's Platform

The twin observes one platform: one GitHub organization, one Octopus space, and an Azure subscription with its resource groups. Which platform comes from a **platform definition**, a JSON file. Without one, the twin observes cmdemo1, whose definition is [`docs/platforms/cmdemo1.platform.json`](../platforms/cmdemo1.platform.json); a test keeps that file identical to the built-in default. [`docs/platforms/contoso.platform.json`](../platforms/contoso.platform.json) is a complete example for a second client.

One twin instance observes one platform. To observe two platforms, deploy two twins, each with its own slug, resource group and database.

## 1. What the Twin Needs From the Client

| Access | Used for | Minimum |
| --- | --- | --- |
| GitHub token (`GH_PAT`) | Reads repositories, pull requests, workflow runs, check runs, issues and the project board; registers repository webhooks | Read access to the observed repositories, repository webhooks (read/write), and organization projects (read) if a board is used. The twin keeps itself under 1,500 REST calls an hour |
| Octopus API key (`OCTOPUS_API_KEY`, `OCTOPUS_URL`) | Reads projects, releases, deployments, tasks, runbooks, interruptions and audit events; creates one event subscription to the twin | Read access to the space, plus permission to manage subscriptions in it |
| Azure service principal (`AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`) | Resource Graph and ARM reads of the observed resource groups; deploys the twin's own resources; optionally Event Grid system topics | Reader on the observed resource groups; Contributor on the twin's resource group; push to the registry; Event Grid needs Contributor on the observed groups, so skip it with `ENABLE_EVENT_GRID_DEPLOY=false` if that is not granted |
| `WEBHOOK_SECRET`, `TWIN_API_KEY` | Signing inbound hooks; protecting the query API and MCP | Generated by you; never shared with the observed platform |

The twin is read-only toward the observed platform. The only things it creates there are repository webhooks, one Octopus subscription and, optionally, Event Grid system topics pointing at itself.

## 2. Write the Platform Definition

Copy `docs/platforms/contoso.platform.json` to `docs/platforms/<slug>.platform.json` and replace every value. Lines starting with `//` are comments.

| Field | Meaning |
| --- | --- |
| `platformName`, `systemSlug`, `systemName` | Display names. `systemSlug` is short (it names the twin's Azure resources: `ca-<slug>-twin`, `sql-<slug>-twin-…`) |
| `twinName` | The twin's own name: health, user agent, MCP server and Octopus subscription. Defaults to `<slug>-digitaltwin` |
| `gitHub.org`, `systemRepository`, `twinRepository` | Organization, the GitOps/infra repository, and the twin's own repository |
| `gitHub.observedRepositories` | Every repository to observe: backfill, hooks, reconciliation and the issue sweep |
| `gitHub.incrementalRepositories` | Repositories polled on the short schedule. Empty means all observed repositories |
| `gitHub.retiredRepositories` | Shown as retired even if not archived |
| `gitHub.workItemsProjectNumber`, `workItemsProjectNodeId` | The organization project used as the work board. Use `0` and `""` for none |
| `gitHub.defaultWorkItemRepository` | Repository assumed for board items that do not name one |
| `gitHub.twinHookUrlMarker` | Text in a webhook URL that marks it as this twin's (`<slug>-twin`) |
| `gitHub.statusFeeds` | Files the GitOps repository publishes (cmdemo1: `system.json`, per-stage `versions.json`, and `cost.json`, `containers.json` and `workitems.json` on a `status` branch). An empty path skips that feed; the twin then relies on the APIs alone |
| `octopus.url`, `spaceId`, `spaceSlug` | The Octopus space |
| `octopus.automationUsers` | Octopus users that deploy for automation; their approvals do not count as a person signing off |
| `azure.subscriptionId`, `tenantId` | The subscription |
| `azure.nonprodResourceGroup`, `prodResourceGroup`, `additionalResourceGroups` | Every resource group to observe |
| `azure.acrName`, `acrLoginServer` | Registry the platform's packages come from |
| `pipelines` | One per deployable or repository family. Exactly one must have `isTwinObserver: true`: the twin itself, which is never counted as a platform change |
| `defaultPipelineId` | Pipeline for repositories and projects not mapped below |
| `repositoryPipelines`, `repositoryDeployables` | Short repository name to pipeline id and to deployable |
| `octopusProjectPipelines`, `octopusProjectDeployables` | Octopus project slug or name to pipeline id and to deployable |
| `stages` | Two or three active stages (not `isDeclaredOnly`) in delivery order. The last is production; DORA metrics and failure rates are measured there |
| `hostingBoundaries` | Container Apps environments and similar, with the stages they host |
| `azureStageRules`, `defaultAzureStage` | First match wins: a resource whose name contains a token, or that sits in a listed group, belongs to that stage |

A change chain has three delivery slots: the first stage, the middle stage if there is one, and production. With `dev` and `prod`, the chain is work item, PR, build, release candidate, Octopus release, dev, prod. The dashboard labels the slots with your stage names; the API keeps the slot names `Tdd`, `Uat` and `Prod` as stable identifiers.

The twin validates the definition at startup and refuses to start if anything is wrong, listing every problem. For example: a missing organization, a mapping to an unknown pipeline, no twin observer pipeline, or a stage count other than two or three.

## 3. Try It Locally (no Azure)

```bash
dotnet test cmdemo1-digitaltwin.sln --configuration Release --filter "FullyQualifiedName~Platform"

docker compose up -d sqlserver
export ConnectionStrings__TwinDb='Server=localhost,1433;Database=twin_contoso;User Id=sa;Password=LocalDev_Tw1n!Only;TrustServerCertificate=True'
export TWIN_API_KEY=local-key WEBHOOK_SECRET=local-secret Twin__EnableBackgroundWorkers=false
export Twin__Platform__File=$PWD/docs/platforms/contoso.platform.json   # absolute: dotnet run starts in the project folder
dotnet run --project src/DigitalTwin.Api
curl -s http://localhost:5000/health                                         # service: contoso-digitaltwin
curl -s -H 'X-Twin-Key: local-key' http://localhost:5000/api/twin/summary | jq '{platformName, systemSlug, stages: [.stages[].stage.name]}'
```

`AnotherPlatformTests` does the same in CI: it boots the twin on the Contoso definition and checks that a release delivered to dev and then prod becomes a delivered change chain.

## 4. Deploy a Twin for the Platform

The twin deploys itself to a resource group of its own; it is not one of the platform's deployables.

1. **Repository secrets** (names are the same for every platform): `AZURE_CLIENT_ID`, `AZURE_CLIENT_SECRET`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, `OCTOPUS_URL`, `OCTOPUS_API_KEY`, `GH_PAT`, `WEBHOOK_SECRET`, `TWIN_API_KEY`.
2. **Repository variables**, which override cmdemo1's defaults in `.github/workflows/ci-deploy.yml`:

| Variable | Example | Used by |
| --- | --- | --- |
| `TWIN_SYSTEM_SLUG` | `contoso` | Bicep `systemSlug` (resource names), image path `<slug>/digitaltwin`, hook matching |
| `TWIN_RESOURCE_GROUP` | `rg-contoso-dev` | Where the twin is deployed |
| `TWIN_ACR_NAME` | `acrcontoso` | Registry for the twin image |
| `TWIN_PLATFORM_FILE` | `docs/platforms/contoso.platform.json` | Passed to Bicep as `platformJson`, which sets the Container App setting `Twin__Platform__Json` |
| `TWIN_GITHUB_ORG` | `contoso-retail` | Webhook registration |
| `TWIN_OCTOPUS_SPACE` | `Spaces-42` | Octopus subscription |

3. Push to `main`. The workflow builds a release candidate, deploys `infra/main.bicep`, and registers hooks and the Octopus subscription (`scripts/register-hooks.sh`). It then runs the health gate: Healthy at the new version, 0 dead letters, database under budget, MCP answering. The database is Azure SQL Basic; raw events older than the retention window, or beyond the size budget, move to a Blob archive in the same resource group.

To deploy through the platform's own Octopus instead, see [docs/octopus-apply.md](../octopus-apply.md). The Terraform there takes `system_slug`, `github_org`, `space_id` and `platform_file`.

## 5. Check the Twin Is Observing the Right Platform

- `/health` reports the twin's name and version.
- `/api/twin/summary` shows your platform name, pipelines and stages.
- `/api/reconciliation` compares the twin with GitHub and Octopus every day. Drift right after the first backfill is expected; it should settle.
- `/api/intake/status` should show `deadLetterCount: 0`.
- The dashboard header, swim-lane columns, chain player and before/after comparison use your stage names.

## What Does Not Change Between Platforms

- The event model: CDEvents-style journal events and `twin.state.observed`.
- Change chains, DORA metrics, time travel, alerts (an outgoing webhook, off until you set a URL), and the shadow rebuild.
- The API and MCP tools.
- The vocabulary: the twin is a **platform** observer one level above the system it watches.
